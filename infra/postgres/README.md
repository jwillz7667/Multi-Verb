# Postgres — schema & migrations

Postgres is **Railway-managed in production**, **Docker-managed
locally** (see `../docker-compose.dev.yml`). Schema is the single
source of truth for both services:

- `services/engine` reads/writes via SQLAlchemy 2.0 async + asyncpg.
- `apps/web` reads/writes via Prisma. Prisma's `schema.prisma` is
  generated by `prisma db pull` against this live schema — never
  hand-edited. CI fails if the two drift.

## Layout

```
infra/postgres/
├── README.md                      # this file
└── migrations/
    ├── env.py                     # Alembic runtime config
    ├── script.py.mako             # template for `alembic revision`
    └── versions/
        └── 20260516_1030_0001_initial_health_table.py
```

The Alembic CLI config lives at `services/engine/alembic.ini` (so
`uv run alembic` works from the engine's project root); its
`script_location` points back here.

## Run

```bash
# from services/engine/
export DATABASE_URL_DIRECT=postgresql://verbio:verbio@localhost:5432/verbio

# show current revision
uv run alembic current

# apply pending migrations
uv run alembic upgrade head

# generate a new revision (autogenerate is no-op until Phase 2 metadata lands;
# hand-author the upgrade()/downgrade() bodies)
uv run alembic revision -m "describe the change"
```

**Always use `DATABASE_URL_DIRECT` (port 5432) for Alembic, never
`DATABASE_URL_POOLED` (port 6543).** pgBouncer transaction mode
rewrites prepared-statement names, which breaks Alembic's
introspection. The pooled URL is for serverless request handlers.

## Phase 0 done-when

- `_health` table exists in the local dev DB.
- `uv run alembic current` reports `0001_initial_health (head)`.
- Engine and web both have credentials and connectivity to the same
  database (verified via the `_health` row).

## After Phase 2

When SQLAlchemy models land in `services/engine/verbio_engine/persistence/models.py`:

1. Update `env.py` to import `Base.metadata` instead of the empty
   placeholder.
2. Autogenerate becomes useful: `uv run alembic revision --autogenerate -m "..."`.
3. Review the generated diff carefully — autogenerate misses
   constraint changes, type changes on existing columns, and any
   non-DDL data migration.
